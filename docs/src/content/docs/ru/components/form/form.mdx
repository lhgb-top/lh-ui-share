Сами по себе элементы формы данные не собирают — **валидация и связывание ошибок** являются главной ценностью формы. `core/form` предоставляет три вещи: движок правил (`validateFormField`), функцию получения значения (`getFormFieldValue` с поддержкой точечных путей) и пакет атрибутов для связывания ошибок (`getFormFieldAria`). Он намеренно **не включает общую оркестровку формы** (регистрация полей, момент отправки, сброс) — это обязанности компонента `LhForm` на UI-слое.

## Когда использовать

- В каждой платформе реализованы `LhForm` / `LhFormItem`: любые сценарии ввода, требующие валидации.
- Сценарии, где нужно связать ошибку валидации с программой чтения экрана (`aria-invalid` + `aria-describedby`).
- **Не использовать для**: одиночного поля с простой валидацией без межпольных зависимостей (возможно, хватит собственного `required` компонента); при сложном графе межпольных зависимостей (вроде «если A равно x, то B обязательно, а C должно равно D») выражайте это пользовательской функцией `validator`, а не пытайтесь комбинировать несколько встроенных правил.

## Импорт

```ts
import {
  getFormFieldValue,
  isEmptyValue,
  validateFormField,
  getFormFieldErrorId,
  getFormFieldAria,
} from '@lh-ui/share/core/form'
import type { LhFormRule, LhFormState } from '@lh-ui/share/core/form'
```

## Замысел дизайна

**Три ключевых решения движка правил**:

1. **Пустое значение заботит только required** — для не обязательного поля с пустым значением **все правила пропускаются**, в соответствии с соглашением распространённых библиотек (Element / Ant Design): не заполнил — нет и ошибки. Это значит, что `type: 'email'` не сообщит «Неверный формат email» для пустой строки — намерение обязательности выражается через `required`.

2. **Асинхронные правила не сокращают проверку** — это поведенческое отличие от старой реализации и самое тонкое место модуля. `validator` может возвращать Promise. Старая реализация после первого thenable **пропускала все последующие правила**, из-за чего «проверка длины после асинхронной проверки email на уникальность silently проглатывалась». Новая реализация оборачивает каждое правило в лениво вычисляемую функцию (`RuleCheck`), при обнаружении thenable приостанавливается и **продолжает вычисление последующих правил**, а в конце объединяет все ошибки в один Promise. Первая же синхронная ошибка по-прежнему возвращается немедленно (сокращение по синхронным ошибкам, без сокращения по асинхронным правилам).

3. **Синхронно выбрасывающий validator трактуется как неудача валидации** — берётся `error.message` в качестве текста ошибки, и она не пробрасывается как неперехваченное исключение. Когда пользователь ошибся в написании пользовательского валидатора (и там выбросился TypeError), форма ведёт себя как «валидация этого поля не пройдена», а не роняет страницу.

**Приоритет текста required**: для пустого значения сначала ищется «обязательное правило с явно предоставленным message», иначе берётся первое обязательное правило. Эта обработка исправляет реальный bug — компонентный слой (form item) при истинном атрибуте `required` **синтезирует правило без message** `{ required: true }`, и если оно стоит раньше пользовательского правила с message, `find` найдёт синтезированное правило и откатится к стандартному тексту, **проглатывая пользовательский текст**.

**Точечный путь в `getFormFieldValue`**: `'user.address.city'` разворачивается послойным reduce; если на пути встречается не-объект (null / примитив), возвращается undefined без возбуждения исключения. Благодаря этому поле формы можно напрямую привязать к вложенной модели, не выравнивая данные вручную на UI-слое.

**Критерии `isEmptyValue`**: undefined / null / пустая строка / пустой массив считаются пустыми; **строка из пробелов и пустой объект не считаются пустыми** — семантика пробелов определяется компонентным слоем через trim при необходимости, core не принимает этого решения за бизнес.

## Таблица функций

| Функция | Сигнатура | Возвращаемое значение | Назначение |
| --- | --- | --- | --- |
| `getFormFieldValue` | `(model, prop: string) => unknown` | значение поля | точечный путь, при отсутствии undefined |
| `isEmptyValue` | `(value: unknown) => boolean` | пусто ли | четыре пустых состояния |
| `validateFormField` | `(value, rules?, model, requiredMessage?) => string \| undefined \| Promise<string \| undefined>` | текст ошибки / undefined | движок правил |
| `getFormFieldErrorId` | `(prop: string) => string` | id элемента | соответствует aria-describedby |
| `getFormFieldAria` | `(options: { prop, error?, required? }) => LhAriaAttrs` | пакет aria-атрибутов | invalid + describedby + required |

## Определения типов

```ts
export interface LhFormRule {
  required?: boolean
  message?: string
  trigger?: string  // момент запуска (blur / change / submit); core его не интерпретирует, UI-слой фильтрует правила по событиям
  /** Встроенная проверка типа; для пустых значений пропускается (тот же принцип, что у required) */
  type?: 'string' | 'number' | 'boolean' | 'array' | 'email' | 'url'
  pattern?: string | RegExp       // регулярное выражение (применимо только к строковым значениям)
  min?: number                    // нижняя граница числа или минимальная длина string/array
  max?: number                    // верхняя граница числа или максимальная длина string/array
  len?: number                    // точная длина (string/array)
  /** Пользовательский валидатор: возвращает текст ошибки, при прохождении не возвращает; поддерживает асинхронность */
  validator?: (value: unknown, model: Record<string, unknown>) => string | undefined | Promise<string | undefined>
}

export interface LhFormState {
  model: Record<string, unknown>
  rules?: Record<string, LhFormRule[]>
}
```

**Двойная семантика `min` / `max`** — это проектировочное удобство: числовые значения сравниваются по величине, а строки/массивы — по длине. Плата — меньшая точность типов, но выгода от лаконичности настройки правил больше (`{ min: 6, message: 'Минимум 6 символов' }` работает и для пароля, и для количества людей).

## Доступность

`getFormFieldAria` — это «последняя миля» доступности формы: при неудачной валидации ошибка связывается с элементом управления, и программа чтения экрана зачитывает «Недопустимый ввод, ошибка: …».

```ts
getFormFieldAria({ prop: 'username', error: 'Имя пользователя обязательно', required: true })
// { 'aria-invalid': true, 'aria-describedby': 'lh-form-error-username', 'aria-required': true }

getFormFieldAria({ prop: 'username', required: true })
// { 'aria-required': true } (без ошибки пустой элемент не связывается)

getFormFieldAria({ prop: 'username' })
// {} (при отсутствии состояния — пустой объект)
```

Сопутствующие соглашения:

- Элемент с текстом ошибки должен рендериться с id из `getFormFieldErrorId(prop)` — на него указывает `aria-describedby`.
- **Синхронизация `aria-describedby`**: атрибут выводится, только если у error есть значение (чтобы не ссылаться на несуществующий пустой элемент), поэтому пакет атрибутов и текст ошибки должны обновляться в одном кадре.
- Для обязательных полей выводится `aria-required`, чтобы программа чтения экрана сообщала «обязательно» ещё при входе в элемент управления.
- Смысл `trigger` для доступности: валидацию по blur не стоит прерывать посередине ввода (сообщать об ошибке на каждый введённый символ — плохой опыт); запуск по change подходит для лёгких сценариев «вводим — проверяем».

## Примеры использования

```ts
import { validateFormField, isEmptyValue, getFormFieldValue } from '@lh-ui/share/core/form'

isEmptyValue('')           // true
isEmptyValue([])           // true
isEmptyValue('  ')         // false (строка из пробелов не считается пустой)
isEmptyValue({})           // false (пустой объект не считается пустым)
isEmptyValue(0)            // false (0 — допустимое значение!)

getFormFieldValue({ user: { name: 'lh' } }, 'user.name')   // 'lh'
getFormFieldValue({ user: null }, 'user.name')             // undefined (на пути встретился не-объект)
getFormFieldValue({}, 'missing')                           // undefined
```

```ts
// Обязательное поле
validateFormField('', [{ required: true, message: 'Имя пользователя обязательно' }], {})
// 'Имя пользователя обязательно'

// Необязательное пустое значение: все правила пропускаются
validateFormField('', [{ required: false, type: 'email', message: 'Неверный формат email' }], {})
// undefined

// Встроенный тип + длина
validateFormField('ab', [{ min: 6, message: 'Минимум 6 символов' }], { username: 'ab' })
// 'Минимум 6 символов'

// Регулярное выражение
validateFormField('123', [{ pattern: /^\d{4}$/, message: '4 цифры' }], {})
// '4 цифры'

// Пользовательский синхронный валидатор
validateFormField('abc', [{
  validator: (v) => (v as string).includes('@') ? undefined : 'Должно содержать @',
}], {})
// 'Должно содержать @'

// Пользовательский валидатор выбрасывает ошибку: трактуется как неудача валидации
validateFormField('x', [{ validator: () => { throw new Error('Валидатор сломался') } }], {})
// 'Валидатор сломался'

// Асинхронный валидатор (без сокращения: последующие синхронные правила всё равно вычисляются)
validateFormField('ab', [
  { validator: async (v) => await checkUnique(v) ? undefined : 'Уже занято', message: 'x' },
  { min: 6, message: 'Минимум 6 символов' },
], {})
// Promise<[первая ошибка из 'Уже занято', 'Минимум 6 символов']>
```

```vue
<!-- Vue3: типичное подключение form-item -->
<script setup>
const error = ref('')
async function validate(trigger: string) {
  const rules = (props.rules ?? []).filter((r) => !r.trigger || r.trigger === trigger)
  error.value = (await validateFormField(
    getFormFieldValue(props.model, props.prop),
    rules,
    props.model,
    t('form.required'),
  )) ?? ''
}
</script>

<template>
  <div class="lh-form-item" :class="{ 'is-error': error }">
    <label class="lh-form-item__label" :for="inputId">{{ label }}</label>
    <div class="lh-form-item__content">
      <slot :aria-props="getFormFieldAria({ prop, error, required })" />
      <p
        v-if="error"
        :id="getFormFieldErrorId(prop)"
        class="lh-form-item__error"
        role="alert"
      >
        {{ error }}
      </p>
    </div>
  </div>
</template>
```

## Замечания

- **`0` / `false` — не пустые значения**: `isEmptyValue(0)` возвращает false. Это самая частая яма — «количество 0» является допустимым вводом, и `required` не должен сообщать об ошибке. Аналогично `false` для флажка является допустимым значением.
- **Второй параметр `validator` — вся model**: межпольная валидация (например, подтверждение пароля) делается через него, не нужно захватывать старое значение в замыкании.
- **Дебаунс асинхронной валидации**: если `validator` отправляет запрос, UI-слой должен делать дебаунс (обычно 300 мс) и обрабатывать гонку «запрос вернулся, а поле уже изменилось» — core этим не занимается, и возврат устаревшего текста ошибки ложится на вызывающую сторону.
- **`trigger` интерпретируется UI-слоем**: core только хранит объявление и не использует его. Компонентный слой фильтрует правила по событиям (blur/change/submit) и только потом передаёт их в `validateFormField`.
- **`requiredMessage` — универсальный запасной текст**: обычно берётся из языкового пакета (`form.required`) и используется, только если у правила `message` равен undefined; явно заданная пустая строка `message: ''` тоже используется как есть (не считается пропущенной).
- **Первая ошибка при нескольких правилах**: синхронные правила сокращают проверку (первое срабатывание немедленно возвращается), асинхронные вычисляются все, после чего берётся первая разрешённая ошибка. Порядок показа ошибок соответствует порядку в массиве правил.
- **prop вложенного поля**: `'user.name'` используется и для получения значения, и для генерации error id (`lh-form-error-user.name`) — точку в id нужно экранировать в CSS-селекторах; учитывайте это при работе с `document.getElementById` или `querySelector`.
