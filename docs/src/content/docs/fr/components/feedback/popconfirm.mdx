Supprimer, soumettre, publier — ce genre d'opérations « difficiles à annuler une fois faites » exigent une seconde confirmation de l'utilisateur. `dialog` est trop lourd (modale, vole le focus, masque) ; `popconfirm` fait apparaître une petite bulle à l'endroit même : une phrase + deux boutons, et elle disparaît dès la confirmation. C'est le composant dont le **poids d'interaction se situe exactement entre tooltip et dialog**.

## Quand l'utiliser

- Chaque framework implémente `<LhPopconfirm>` : supprimer une ligne, annuler une opération, vider des données, soumettre une commande.
- Les confirmations en deux étapes **légères, sur place et avec peu de marge de retour en arrière**.
- **À ne pas utiliser pour** : des conséquences assez graves pour exiger toute l'attention de l'utilisateur (utilisez `dialog` — le masque modal force la concentration) ; une simple information (utilisez `tooltip` / `message`) ; une confirmation nécessitant la saisie d'un motif ou le cochage d'options (utilisez `dialog` avec un formulaire).

## Intentions de conception

**Le ton par défaut est warning, pas info** : `LH_POPCONFIRM_TYPE_DEFAULT = 'warning'` — l'apparition d'une bulle de confirmation signifie presque toujours « il y a un risque », le ton par défaut doit donc être l'avertissement. info est laissé aux confirmations purement informatives (« Marquer comme lu ? »), danger aux opérations irréversibles (« La suppression est irréversible »).

**Trois tons, trois icônes** : info → `info`, warning → `warning`, danger → `error` (le nom de l'icône est error et non danger — le nommage de la bibliothèque d'icônes est error, c'est un mapping entre deux nomenclatures). Un type inconnu retombe sur warning.

**`role="alertdialog"` plutôt que `"dialog"` de popover** : alertdialog est, dans ARIA, « la boîte de dialogue exigeant une réponse immédiate de l'utilisateur » — les lecteurs d'écran l'**annoncent en priorité** (caractère interruptif semblable à alert, mais en exigeant un choix). Cela correspond mieux que dialog à la sémantique « j'attends votre décision ».

**Le contrat d'événements confirmer/annuler est dans la couche UI** : core ne fournit que les classes, l'icône, les attributs aria et les délais ; les événements `onConfirm` / `onCancel`, les textes des boutons et l'état de loading appartiennent à la couche UI — parce qu'ils impliquent la communication dans l'arbre des composants (emit), que core ne touche pas aux API du framework.

**Les délais suivent popover** : les valeurs par défaut de `getDefaultDelay` sont 200/100, identiques à popover — la bulle de confirmation admet elle aussi le déclenchement au survol, et le pointeur doit pouvoir y entrer.

## Définitions de types

```ts
export type LhPopconfirmType = 'info' | 'warning' | 'danger'
export type LhPopconfirmTrigger = 'click' | 'hover' | 'focus' | 'manual'

export interface LhPopconfirmState {
  type?: LhPopconfirmType
  trigger?: LhPopconfirmTrigger

```

## Accessibilité

```ts
getPopconfirmPopperAria('pc-1')
// { role: 'alertdialog', id: 'pc-1' }
getPopconfirmTriggerAria(true, 'pc-1')
// { 'aria-expanded': true, 'aria-controls': 'pc-1', 'aria-haspopup': 'true' }
```

- **L'annonce de l'alertdialog** : quand un lecteur d'écran rencontre un alertdialog, il en annonce immédiatement le contenu (aria-labelledby ou le texte interne) — **l'utilisateur n'a pas besoin d'aller le lire** — c'est ce qui le rend plus contraignant que dialog, conforme à l'intention « en attente de votre confirmation ».
- **Les boutons doivent avoir un texte explicite** : « Confirmer / Annuler » est préférable à « OK / NO » ou à des boutons icônes. Avec le ton `danger`, le texte du bouton de confirmation devrait exprimer la conséquence (« Supprimer » plutôt que « Confirmer »).
- **L'annulation est la direction sûre** : Entrée déclenche-t-elle **confirmer** ou **annuler** par défaut ? La pratique courante est que le focus initial se porte sur le bouton **Annuler** (un seul Tab + Entrée permet une sortie sûre) — pour une opération destructrice, ne placez pas le focus par défaut sur Confirmer. C'est la décision de la couche UI, core n'intervient pas.
- **Esc = annuler** : quand `canCloseOnEscape` l'autorise, Esc devrait déclencher onCancel et pas seulement fermer — sémantiquement, « fermer la bulle de confirmation » c'est « ne pas confirmer ».
- **Icône aria-hidden** : la sémantique de l'icône (warning/error) est déjà portée par le texte, l'icône elle-même est décorative, pour éviter que le lecteur d'écran annonce « avertissement » en double.

## Remarques

- **Le titre doit exprimer la conséquence** : « Confirmer la suppression ? » est un mauvais texte (la conséquence n'est pas dite) ; « La suppression est irréversible. Confirmer la suppression de cette ligne ? » est un bon texte. C'est le cœur de l'expérience popconfirm.
- **Ne pas imbriquer** : un popconfirm dans un popconfirm laisse l'utilisateur perplexe sur la couche qu'il est en train de confirmer. Pour des confirmations multi-étapes, utilisez dialog.
- **Quand le déclencheur est un bouton désactivé** : un bouton `disabled` ne déclenche pas d'événement (limitation native) et popconfirm ne peut pas s'ouvrir — le métier doit le gérer lui-même (envelopper dans un élément non désactivé, ou ne pas rendre le popconfirm quand désactivé).
- **Le timing de fermeture de la confirmation asynchrone** : pendant le traitement du confirm, les deux boutons devraient être désactivés + un masque pour empêcher les doubles clics ; en cas d'échec, **garder la bulle ouverte** et signaler l'erreur, et fermer seulement en cas de succès. Fermer la bulle de façon synchrone dans onConfirm est un bug courant.
- **La coopération avec message** : une fois la confirmation accomplie, utilisez `message` pour un retour de succès (« Supprimé ») ; les deux forment la chaîne standard « confirmer → exécuter → retour ».
- **Le déclenchement au survol sur mobile** : comme popover, l'écran tactile n'a pas de survol. Le déclenchement par clic est la valeur par défaut multiterminale.
- **`role="alertdialog"` n'apporte pas la sémantique implicite des boutons** : la zone des boutons doit être rendue avec de vrais `<button>` (pas des div + onclick), pour que les utilisateurs au clavier puissent les actionner.
