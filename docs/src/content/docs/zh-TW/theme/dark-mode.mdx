lh-ui 的所有元件**預設支援明色與暗色**。這不是事後追加的主題，而是令牌系統的設計前提。

## 切換機制

暗色的開關是 CSS 選擇器，不是 JS：

```scss
// styles/theme/common/var-dark.scss
[data-theme='dark'],
.dark {
  --lh-bg-color: #2A2520;
  --lh-text-primary: #E8E0D8;
  // ... 118 條覆蓋
}
```

兩種觸發方式：

```html
<!-- 方式一：data 屬性（推薦，語義清晰） -->
<html data-theme="dark">

<!-- 方式二：class（相容舊程式碼 / 第三方切換庫） -->
<body class="dark">
```

UI 層（各庫的 ConfigProvider 或業務程式碼）只要切這個屬性 / 類別名，**所有元件立即變色**——CSS 變數是執行時求值的，沒有重渲染開銷。

```ts
function toggleDark(isDark: boolean) {
  document.documentElement.dataset.theme = isDark ? 'dark' : 'light'
}
```

## 暗色是覆蓋層

暗色檔案只寫 **118 條**，不是完整一套 185 條。只覆蓋需要翻轉的令牌，其餘沿用明色值。

設計原則是**語義令牌重指向，而非逐元件重寫**：

```scss
// ✅ 好的做法：暗色下指向暗色語義令牌
[data-theme='dark'],
.dark {
  --lh-menu-item-color: var(--lh-text-primary);
  --lh-table-cell-color: var(--lh-text-primary);
}

// ❌ 壞的做法：在暗色裡寫死一個具體顏色
[data-theme='dark'],
.dark {
  --lh-menu-item-color: rgba(255, 255, 255, 0.85);   // 與 text-primary 脫鉤，後續調色要改兩處
}
```

## 編譯期烤死陷阱

這是暗色模式**最容易踩的坑**，也是 `verify:styles` 第 7 項存在的理由。

### 陷阱原理

`var.scss` 裡值形如 `#{$lh-foo}` 的令牌：

```scss
// var.scss
:root {
  --lh-menu-item-color: #{$lh-menu-item-color};   // SCSS 變數在編譯期被替換成具體明色值
}
```

SCSS 變數在**編譯期被烤死成字面值**，等價於：

```scss
:root {
  --lh-menu-item-color: rgba(0, 0, 0, 0.88);   // 暗色下不會自動翻轉！
}
```

結果：暗色模式下選單 / 表格 / 時間軸的文字沿用明色值，**黑底黑字，不可見**。這類缺口曾真實出現過，補缺記錄見 0.4.0 的 changeset。

### 解法

在 `var-dark.scss` 顯式重新指向暗色語義令牌：

```scss
[data-theme='dark'],
.dark {
  --lh-menu-item-color: var(--lh-text-primary);
}
```

### 鏈式回落是執行時求值，安全

元件 SCSS 裡的鏈式回落：

```scss
.lh-button {
  color: var(--lh-foo, var(--lh-bar, #333));
}
```

`var()` 的回落是**執行時求值**的：只要鏈上任一令牌有暗色覆蓋，整個鏈就跟隨翻轉。**無需重複宣告**。

對照表：

| 寫法 | 求值時機 | 暗色行為 |
| --- | --- | --- |
| `var(--lh-foo, fallback)` | 執行時 | ✅ 鏈上令牌有暗色覆蓋即翻轉 |
| `#{$lh-foo}`（SCSS 內插） | 編譯期 | ❌ 烤死成明色，需在 var-dark 顯式重指向 |
| `mix($lh-a, $lh-b)` 等 SCSS 函式 | 編譯期 | ❌ 同上 |

## 深主色預設的暗色提亮

五個內建預設中，深主色的（青花瓷 / 朱砂 / 水墨）在暗色下主色會「沉進」頁面底色。`buildPresetDarkVars` 自動處理：

判定規則：`--lh-primary-color` 相對暗色頁面底 `#1A1A2E`（`DARK_PAGE_BG`）的對比度小於 3（`DARK_PRIMARY_CONTRAST_THRESHOLD`）即判定深主色，然後：

```css
[data-theme='dark'],
.dark {
  --lh-primary-color: color-mix(in srgb, <字面值> 55%, #fff);   /* 提亮 55% */
  --lh-primary-color-hover: color-mix(in srgb, var(--lh-primary-color) 70%, #fff);
  --lh-primary-color-active: color-mix(in srgb, var(--lh-primary-color) 85%, #000);
  --lh-color-on-primary: #101410;   /* 提亮後白字對比度反而不足，改墨字 */
  --lh-primary-color-bg: color-mix(in srgb, var(--lh-primary-color) 25%, transparent);
  --lh-selected-color: color-mix(in srgb, var(--lh-primary-color) 40%, #fff);
}
```

**為什麼主色提亮用字面值不用 `var()`**：`color-mix(in srgb, var(--lh-primary-color) 55%, #fff)` 會形成 CSS 自引用循環（`--lh-primary-color` 的值裡引用了自己）。所以這一條**代入字面值**，其餘用 `var()` 跟隨當前主色。

淺主色預設（松花綠 / 藤黃）不需要提亮，但仍會拿到 `--lh-primary-color-bg` 與 `--lh-selected-color` 的暗色重定義。

## 預設注入的順序語義

`buildPresetStyleText` 生成的文字是 `:root { ... }` 塊在前、`[data-theme='dark'], .dark { ... }` 塊在後。**同特異性下後者勝**，所以淺主色預設在 `:root` 裡宣告的 `--lh-selected-color` 明色值不會洩漏進暗色。

這也是「只能寫 `<style>` 不能寫內聯 style」的根因——內聯 style 特異性 1,0,0,0 壓過 `var-dark.scss` 的整段暗色變數，暗色直接失效（詳見 [主題總覽](/theme/overview#注入約束只能寫-style不能寫內聯-style)）。

## 如何驗證暗色完備性

三個手段，從弱到強：

1. **`pnpm verify:styles` 第 7 項（暗色可達性）**：靜態掃描，找出「明色烤死但 var-dark 無覆蓋」的令牌。這是 CI 門禁。
2. **`pnpm verify:theme`（AA 4.5:1）**：讀 `es/` 產物，算預設主題在明暗兩色下的對比度。需先 `pnpm build`。CI 不跑，手動把守。
3. **目視檢查**：docs 站 / 各庫 playground 切暗色模式逐元件看。

新增令牌時的自我檢查清單：

- [ ] 這個令牌暗色下需要翻轉嗎？
- [ ] 需要的話在 `var-dark.scss` 補了覆蓋嗎？
- [ ] 它的值是 `#{$lh-*}` 內插嗎？（是 → 必須補暗色覆蓋）
- [ ] 元件裡消費它用的是 `var(--lh-x, fallback)` 鏈嗎？

## 已知遺留

暗色完備性在 0.4.0 做過一次系統性補缺（選單 / 表格 / 時間軸等文字不可見問題，見 changeset）。剩餘已知項隨「高度令牌專項」待後續處理。
