A tree is the universal container for hierarchical data: file directories, organizational structures, permission trees, cascading menus. Its difficulty lies in **state management of a recursive structure** — expanding, checking, and lazy loading are all operations on an entire subtree, and it also has to handle circular references in the data, disabled nodes, and the indeterminate state. `core/tree` converges this set of algorithms with pure functions + immutable updates.

## When to use

- Each framework implements `LhTree`: directory browsing, permission assignment, organizational structure display, category filtering.
- Scenarios where hierarchical data needs expanding / collapsing, checking (including parent-child linkage), and lazy loading.
- **Don't use it**: flat categories of two levels or fewer (a cascader or a segmented control is simpler); linear lists (use `virtual-list`).

## Design intent

**Rendering is flattening**: a tree is essentially a **list with indentation levels** in the UI. `flattenTree` does a depth-first traversal, expanding only the subtrees hit by `expandedKeys`, and outputs a flat array (each item carries `level` / `parentKey` / `ancestorKeys`). The UI layer does a `v-for` over a one-dimensional array — this is much simpler than a recursive component and is naturally compatible with virtual scrolling.

**Ancestor-chain deduplication vs global deduplication**: this module's recursive functions generally use an **ancestor-chain seen** set (`ancestors` / `nextSeen` passed down layer by layer) rather than a global Set. The cost is that the protection is only valid within a single call; the benefit is that **legitimately shared subtrees in a DAG are not mistakenly skipped**, and there is no cross-instance state leakage. Note the difference from `table`'s `flattenLeafColumns` (which uses a global seen) — a table's DAG sharing must emit only once (column-count alignment), while a tree's DAG sharing should be counted once per distinct path.

**Disabled nodes do not count toward the all-selected denominator**: `collectCheckableLeafKeys` skips disabled subtrees — otherwise, after the parent is checked, a missing disabled descendant would keep it **permanently indeterminate**, never able to become fully selected. This is a class of real UX bug.

**Unloaded non-leaf nodes**: when `isLeaf !== true` and there is no `children`, `collectCheckableLeafKeys` returns an empty array, but `toggleCheckKeys` writes the node's **own key** into `checkedKeys` — in a lazy-loading scenario the user can check a node whose children have not loaded yet, and after loading it is up to the UI layer whether to cascade.

**`moveTreeFocus` is @deprecated**: the navigation algorithm has converged on `core/shared/keyboard.getNextListIndex`; this shell retains the old signature and the existing "fall back to the first item when the current value is invalid" semantics.

## Type definitions

```ts
export interface LhTreeNode {
  key: string
  label: string
  children?: LhTreeNode[]
  disabled?: boolean
  isLeaf?: boolean       // inferred from children when omitted
}

export interface LhFlatTreeNode {
  node: LhTreeNode
  key: string
  level: number                 // 0-based
  parentKey: string | null
  ancestorKeys: string[]        // ancestor chain (excluding itself)
  isLeaf: boolean
}

export type LhTreeCheckState = 'checked' | 'indeterminate' | 'unchecked'
```

## Accessibility

`getTreeAria` / `getTreeNodeAria` emit the complete semantics of the APG treeview pattern:

```ts
getTreeAria('lh-tree-1')  // { role: 'tree', id: 'lh-tree-1' }

getTreeNodeAria({ level: 2, expanded: true, selected: true, checked: 'indeterminate' })
// { role: 'treeitem', 'aria-level': 2, 'aria-expanded': true,
//   'aria-selected': true, 'aria-checked': 'indeterminate' }

getTreeNodeAria({ level: 1, leaf: true })
// { role: 'treeitem', 'aria-level': 1 }  ← leaf nodes do not emit aria-expanded
```

- `aria-level` is 1-based (note that `flattenTree`'s `level` is 0-based — **add 1** when passing it to aria).
- **Leaf nodes do not emit `aria-expanded`** — avoiding a meaningless `aria-expanded="false"` is an explicit APG requirement.
- The three values of `aria-checked`: `true` / `false` / `'indeterminate'` (a string).
- Keyboard interaction (APG treeview): ↑/↓ move between visible nodes, → expands / enters a child node, ← collapses / returns to the parent, Home/End jump to the first/last, Enter triggers selection.
- **The source of `aria-level` after flattening**: `flattenTree`'s `level + 1`; do not infer it backwards from the DOM indentation depth.

## Usage examples

```ts
import { flattenTree, toggleCheckKeys, getNodeCheckState } from '@lh-ui/share/core/tree'

const tree = [
  { key: '1', label: 'R&D', children: [
    { key: '1-1', label: 'Frontend', children: [{ key: '1-1-1', label: 'lh-ui' }] },
    { key: '1-2', label: 'Backend' },
  ]},
  { key: '2', label: 'Product' },
]

flattenTree(tree, ['1'])
// [R&D(l0), Frontend(l1), Backend(l1), Product(l0)]
// note that 1-1-1 does not appear: because '1-1' is not in expandedKeys

flattenTree(tree, ['1', '1-1'])
// [R&D, Frontend, lh-ui(l2), Backend, Product]

toggleCheckKeys(tree, [], '1')
// ['1', '1-1', '1-1-1', '1-2'] (cascades to select all descendants, including itself)

toggleCheckKeys(tree, ['1', '1-1', '1-1-1', '1-2'], '1-1-1')
// ['1-2']  —— after unchecking '1-1-1' the cascade backtracks: '1-1' is no longer fully checked and is removed,
// and '1' is no longer fully checked either and is removed (backtracking walks all the way to the root)

toggleCheckKeys(tree, ['1-1'], '1-2')
// ['1-1', '1-2']  —— only backtracks ancestors, leaving other branches untouched

getNodeCheckState(tree[0], ['1', '1-1', '1-1-1', '1-2'])  // 'checked' (all checkable leaves hit)
getNodeCheckState(tree[0], ['1-1-1'])                      // 'indeterminate' (one of two checkable leaves)
getNodeCheckState(tree[0], ['1-1'])                        // 'unchecked' ('1-1' is not a leaf, not counted)
getNodeCheckState(tree[0], [])                             // 'unchecked'
```

## Caveats

- **`level` is 0-based, `aria-level` is 1-based** — this is the easiest thing to get wrong in this module; always `+1` when binding `aria-level`.
- **The valid scope of ancestor-chain deduplication**: the protection is only valid within a single call. Two independent `findTreeNode` calls on the same tree deduplicate independently, and a shared subtree will be traversed twice — this is intentional (legitimate DAG sharing), not a bug.
- **`checkStrictly` (no parent-child linkage)**: `getNodeCheckState` becomes binary, and `toggleCheckKeys` only changes the node's own key without backtracking ancestors. Common in permission-assignment scenarios.
- **The cascading invariant for disabled nodes**: `toggleCheckKeys`'s ancestor backtracking skips disabled parents — their keys are not rewritten by the cascade. If the business needs "a disabled parent can still be selected programmatically", operate on `checkedKeys` directly instead of using this function.
- **`isLeaf` takes precedence over `children`**: a node declared with `isLeaf: true` is treated as a leaf even if it has `children` (common in lazy-loading scenarios: declaring it a leaf blocks expansion).
- **The immutability of `mergeLoadedChildren`**: it returns a new tree and does not modify the passed-in `nodes` — props.data is owned by the consumer, and mutating it directly would break the one-way data flow.
- **The performance of `flattenTree`**: it is recomputed in full every time `expandedKeys` changes. For deep hierarchies and large data volumes, consider memoizing per subtree (the UI layer caches grouped by parentKey).
- **Circular references in the data**: all recursive functions are guarded by ancestor-chain deduplication and will not recurse infinitely — but **the data itself having a cycle is an error in the first place**; deduplication just keeps it from crashing.
