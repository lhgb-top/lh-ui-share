The table is the "heavy weapon" of data display: sorting, filtering, multi-level headers, fixed columns, virtual scrolling, and column resizing — each is its own algorithmic puzzle. `core/table` abstracts all of these into pure functions — the UI layer only binds the results to the DOM. It is one of the component modules with the most functions in this package.

## When to use

- Each framework implements `LhTable`: admin lists, data reports, tables with bulk operations.
- Scenarios where structured data needs sorting / filtering / fixed columns / multi-level headers.
- **Don't use it**: extremely small data sets with no interaction (a simple `descriptions` or a hand-written table is lighter); card-style information feeds (use the `card` layout).

## Design intent

**Nulls last**: `sortTableRows` handles `null` / `undefined` / `NaN` uniformly — they do not participate in normal comparison and are always sorted to the end, **and stay at the end under desc as well**. This is a deliberate product decision: rows with empty data should not jump to the first row and block valid data just because the order is reversed.

**DAG safety for multi-level headers**: `flattenLeafColumns` and `buildHeaderCells` use a **global seen** set rather than a per-ancestor-chain seen — because the same column object may be shared in a DAG-style reference (the same column appearing under two groups), global deduplication guarantees it is emitted only once, so the body's column count matches the header's leaf-cell count. `buildHeaderCells`'s `leafSpan` uses "the number of leaves actually emitted by recursion" rather than an a-priori count, precisely to prevent a shared subtree from being counted twice and throwing off the column count.

**Sticky inheritance for group headers**: `getHeaderStickyOffsets` only lets a group header inherit the offset of its first/last leaf when **all leaf columns in its span are fixed on the same side** — a group header that spans both the fixed zone and the flowing zone cannot be positioned with a single offset, so it is simply not fixed.

**`clampColumnWidth`'s isomorphic overloads**: number in / number out, string in / string out — callers do not need an extra type assertion for an isomorphic transform; NaN returns the lower bound directly (NaN coordinates can appear during a drag).

**`computeVisibleRange` is @deprecated**: the virtual scrolling algorithm has converged on `computeRange` in the shared kernel `core/shared/virtual` (same origin as VirtualList); this function is retained as a compatibility alias for existing references in downstream libraries such as vue2.

## Accessibility

`getTableSortAria` emits `aria-sort`, strictly aligned with the state machine of `cycleSortOrder`:

```ts
getTableSortAria({ sortable: true, sortOrder: 'asc' })    // { 'aria-sort': 'ascending' }
getTableSortAria({ sortable: true, sortOrder: 'desc' })   // { 'aria-sort': 'descending' }
getTableSortAria({ sortable: true })                      // { 'aria-sort': 'none' }
getTableSortAria({ sortable: false })                     // {} (not emitted for non-sortable columns)
```

Note the third case: when unsorted it emits `aria-sort="none"` rather than omitting it — this is an explicit APG requirement, **explicitly declaring "this column is sortable but currently unsorted"**, which lets screen readers hint to the user that a sort action is available on this column.

The remaining conventions (implemented by the UI layer): headers use `<th scope="col">`; fixed columns should not use `tabindex` to create extra focus stops; the pagination area is a separate `nav`; the row-selection checkbox needs an `aria-label` (e.g. "Select row 3").

## Usage examples

```ts
import { cycleSortOrder, sortTableRows, filterTableRows, buildHeaderCells } from '@lh-ui/share/core/table'

cycleSortOrder(undefined)  // 'asc'
cycleSortOrder('asc')      // 'desc'
cycleSortOrder('desc')     // undefined (sort canceled)

const rows = [
  { name: 'Charlie', age: 30 },
  { name: 'Bob', age: null },
  { name: 'Alice', age: 20 },
]
sortTableRows(rows, 'age', 'asc')
// Alice 20 → Charlie 30 → Bob null (empty values are always last)
sortTableRows(rows, 'age', 'desc')
// Charlie 30 → Alice 20 → Bob null (empty values are still last when reversed)
sortTableRows(rows, 'age', undefined)  // a copy in the original order

filterTableRows(rows, [{ column: { prop: 'name' }, values: ['Alice'] }])
// [{ name: 'Alice', age: 20 }]
filterTableRows(rows, [])  // a full copy (no active filters)

// Multi-level headers
const columns = [
  { label: 'Basic info', children: [{ prop: 'name', label: 'Name' }, { prop: 'age', label: 'Age' }] },
  { prop: 'city', label: 'City' },
]
flattenLeafColumns(columns)  // [Name, Age, City] (the body renders against this)
buildHeaderCells(columns)
// Basic info (level 0, leafStart 0, colspan 2), Name (rowspan 2 padded),
// Age (rowspan 2), City (level 0, rowspan 2)
```

## Caveats

- **Row-height consistency is a prerequisite for virtual scrolling**: `computeRange` assumes every row has equal height; if in-row content stretches the height (long text wrapping), virtual scrolling will misalign — do not enable `virtual` for tables with irregular heights.
- **Fixed columns must declare a `width`**: `getStickyOffsets` only converts offsets for numeric px or `'Npx'` strings; units like `'20%'` cannot be converted and accumulate as 0, so fixed columns end up stacked on top of each other.
- **Prerequisites for `resizable`**: it must be a leaf column with a numeric `width`; after resizing, clamp to the lower bound with `clampColumnWidth` before writing it back to the column config.
- **The sort `prop` and data keys**: `sortTableRows` reads `row[prop]`; nested fields (`user.name`) are not supported automatically — use a custom `sorter`.
- **OR within a filter column**: multiple selected values within one column are "or"-related, and different columns are "and"-related — this is the common convention shared with Element.
- **Body column order for multi-level headers**: the body must use `flattenLeafColumns(columns)` rather than `columns`, otherwise the column count will not match the header's leaf cells.
- **DAG-shared columns**: when the same column object is referenced under two groups, the global seen set guarantees it is emitted only once — but **the side effect of sharing one object is that changing it in one place changes it in both**; if you need "same name, different config", deep-copy it.
- **Sorting large data sets is O(n log n)**: sorting tens of thousands of rows per frame will stall; consider server-side sorting (`sortable: 'custom'` as agreed by the UI layer).
- **`getTableSortAria`'s `aria-sort` goes on the `<th>`**, not on every cell of the column.
