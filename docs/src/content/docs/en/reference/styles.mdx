`styles/` is the **single source** of component BEM styles for the whole family ([red line 2](/development/contribution#the-six-red-lines)): 58 component directories plus the `theme/common/` token layer. No UI library may copy the styles out and hand-edit them.

## Directory structure

```
styles/
├── index.scss                  # full aggregation (tokens + all components), one-line import
├── theme/
│   ├── common/
│   │   ├── var.scss            # light tokens (:root, 185 CSS variables)
│   │   ├── var-dark.scss       # dark overrides ([data-theme='dark'], .dark, 118 entries)
│   │   ├── variables.scss      # SCSS variable layer (183 $lh-*, compile-time constants)
│   │   ├── patterns.scss       # traditional Chinese pattern system (6 textures)
│   │   ├── transition.scss     # single source of cross-port transition class names (3 mixins)
│   │   └── …                   # shared mixin / function layer
│   └── index.scss              # theme aggregation entry
├── button/index.scss           # component styles (58 directories)
├── dialog/index.scss
└── …
```

**Each component directory is just one `index.scss`**, imported as `@lh-ui/share/styles/<name>` (vite resolves the directory to index).

## How to import

```ts
// four import forms (see Getting started for details)
import '@lh-ui/share/styles/button'        // a single component
import '@lh-ui/share/styles'                // everything (styles/index.scss)
import '@lh-ui/share/styles/theme'          // theme tokens only
import '@lh-ui/share/styles/theme/common/var-dark'  // down to a specific file
```

Each UI library has its own injection strategy: plus injects the full set at the library entry, while vue2 leaves on-demand importing to the user (see [injection strategies](/guide/injection)).

## BEM conventions

Class names always take the `lh-` prefix plus the three BEM layers:

```scss
.lh-button {                    // Block
  &__text { }                   // Element
  &--primary { }                // Modifier
  &__text--disabled { }         // Element + Modifier
  &.is-loading { }              // state class (is- prefix, no namespace)
}
```

- Names are generated by [createNamespace](/reference/utils#createnamespace--the-bem-namespace), guaranteeing consistency across the whole family.
- **State classes use the `is-` prefix** (`is-loading` / `is-disabled` / `is-open`); they are not BEM modifiers.
- Adding a class name requires updating `docs/src/data/classes.json` in sync (generated by `scripts/gen-docs-data.mjs` scanning `styles/*/index.scss`).

## The three token layers

| Layer | File | Count | Characteristics |
| --- | --- | --- | --- |
| CSS variables (light) | `var.scss` | 185 | `:root { --lh-*: ... }`, overridable at runtime |
| CSS variables (dark) | `var-dark.scss` | 118 | `[data-theme='dark'], .dark { ... }` overriding the light values |
| SCSS variables | `variables.scss` | 183 | `$lh-*`, **baked in at compile time** |

### Components may only consume CSS variables

```scss
// ✅ correct: var() chained fallback, evaluated at runtime
.lh-button--primary {
  color: var(--lh-color-on-primary, #fff);
  background: var(--lh-primary-color, #1677ff);
}

// ❌ wrong: referencing an SCSS variable directly; will not flip in dark mode
.lh-button--primary {
  background: #{$lh-primary-color};
}
```

### The compile-time baking trap

For tokens in `var.scss` whose value looks like `#{$lh-foo}`, the SCSS variable is **replaced with a concrete light value at compile time** and will not flip automatically in dark mode. Such tokens must be explicitly re-pointed at a dark semantic token in `var-dark.scss`:

```scss
// var-dark.scss
[data-theme='dark'],
.dark {
  --lh-menu-item-color: var(--lh-text-primary);   // ← explicit re-pointing
}
```

Gaps of this kind once left menu / table / timeline text in dark mode using the light values, rendering it invisible. `pnpm verify:styles` item 7 (dark accessibility) guards exactly this. Conversely, a component's `var(--lh-foo, var(--lh-bar, #x))` **chained fallback is evaluated at runtime** — as long as some token on the chain has a dark override it is safe, and no duplicate declaration is needed. See [Dark mode](/theme/dark-mode).

## `styles/index.scss` is generated

The full aggregation file is **generated by scanning component directories** via `scripts/build-styles.mjs`, and `verify:styles` checks its consistency — **do not hand-edit it**. A newly added component directory is picked up by the aggregation automatically.

## The deprecated hairline marker

~~1px hairline border declarations must carry a `/* hairline */` line marker~~ — this red line is **deprecated** (uniapp v3 outputs px directly and no longer transpiles rpx, so the marker lost its purpose; see `docs/bugfix-log.md` D-02). The 65 historical markers already inside `styles/` remain as ordinary comments; **new 1px borders need no marker**. Structural borders (2px / 3px) were never marked in the first place.

## Caveats

- **Styles are changed only in this repo**: no UI library may hold a copy of the component scss. Cross-port transition class-name differences are unified by the [transition mixins](/reference/transition-mixins).
- **Colors always take the form `var(--lh-*, fallback)`** — no new hardcoded color values (guarded by the var fallback check in verify:styles).
- **A new component must have `styles/<name>/index.scss`**, otherwise that component gets no style artifact on one of the ports (the build scripts skip it silently, without an error).
- **Dark-mode completeness is a hard requirement**: all components support both light and dark by default, and dark gaps are caught by verify:styles item 7.
